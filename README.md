# Hendy Tools Platform & App Downloader

Hendy Tools is built as a React 19 + Vite single-page application with a Cloudflare Worker edge API and a separate Cloudflare Pages deployment option.

## Production entry point

**Primary Worker URL:** https://hendy-tool-releas.ngogiaidy56.workers.dev/

The Worker name in `wrangler.worker.toml` is intentionally `hendy-tool-releas`. The account's `workers.dev` subdomain must be enabled in Cloudflare for the exact hostname above to resolve.

Useful checks after deployment:

- UI: `/`
- Health: `/healthz`
- API metadata: `/api/v1/meta`
- Release catalog: `/api/v1/releases`
- Update check: `/api/v1/update-check?platform=windows&clientBuild=0`
- Domain overview: `/api/v1/domains`
- Edge telemetry: `/api/v1/telemetry`

## Deployment architecture

- `src/`: React/Vite source and `src/worker.ts`, the Worker entry point.
- `dist/`: compiled frontend assets generated by `npm run build`.
- `functions/api/[[path]].ts`: Cloudflare Pages Functions fallback/API gateway for the Pages deployment.
- `wrangler.worker.toml`: Worker named `hendy-tool-releas`; serves both compiled UI and API at the workers.dev URL.
- `wrangler.toml`: configuration for the independent Pages deployment.
- `server.ts`: optional Express server for Node/Render; Cloudflare does not execute this file.

## GitHub Actions setup

The workflow `.github/workflows/deploy-cloudflare.yml` runs type-checking, unit tests, the Vite build and Wrangler dry-run. It then deploys Pages and the Worker. Every push to `main` deploys both; from Actions you can manually choose `both`, `pages` or `worker`.

In GitHub → repository **Settings → Secrets and variables → Actions**, set:

- `CLOUDFLARE_API_TOKEN`: token with Cloudflare Pages Edit, Workers Scripts Edit and R2 Storage Edit permissions for the intended account.
- `CLOUDFLARE_ACCOUNT_ID`: Account ID from Cloudflare Dashboard.

## Cloudflare Dashboard setup

1. Open [Workers & Pages](https://dash.cloudflare.com/918ff2f016938fc978ed23b96505b21e/workers-and-pages).
2. Ensure the account's `workers.dev` subdomain is enabled and available.
3. Ensure the Pages project `hendy-tool-releas` exists if deploying the Pages target. It uses Wrangler Direct Upload, so don't run a second competing Git-integrated deployment for the same Pages production branch.
4. Push to `main` or run **Actions → Deploy to Cloudflare Pages and Workers → Run workflow** and select a target.

### Manual deployment

Requires Node.js 22+:

```bash
npm install
npm run lint
npm test
npm run build

# The R2 bucket is created by the deploy workflow. For manual deployment, create it once:
npx wrangler@4 r2 bucket create hendy-tool-releases

# Deploy Worker UI + API to the exact workers.dev hostname:
npx wrangler@4 deploy --config=wrangler.worker.toml

# Optional separate Pages deployment (the Pages project must already exist):
npx wrangler@4 pages deploy dist --project-name=hendy-tool-releas --branch=main
```

## Publishing real application binaries

The repository contains release catalog templates but does not contain actual signed Windows installers or Android APKs. The API intentionally reports a release as unavailable until its binary exists in R2. This prevents fake URLs or made-up checksums from being shown as published downloads.

The configured R2 bucket binding is `RELEASES_BUCKET`, bucket `hendy-tool-releases`. Upload actual artifacts using these object keys:

- `windows/3.2.0/HendyToolsPro-3.2.0-Setup.exe`
- `android/3.2.0/HendyToolsMobile-3.2.0.apk`

Example (after creating the genuine artifact):

```bash
npx wrangler@4 r2 object put hendy-tool-releases/windows/3.2.0/HendyToolsPro-3.2.0-Setup.exe --file=./HendyToolsPro-3.2.0-Setup.exe
npx wrangler@4 r2 object put hendy-tool-releases/android/3.2.0/HendyToolsMobile-3.2.0.apk --file=./HendyToolsMobile-3.2.0.apk
```

To publish a verifiable SHA-256 value, attach the computed hash as R2 custom metadata named `sha256` and upload time as `publishedAt`. The API sets `checksumVerified` only when a 64-character hexadecimal SHA-256 value is present.

## Notes

- `npm run build` publishes the frontend only; a React/Vite build does not compile native .exe or .apk binaries.
- The local catalog metadata is a release template, not proof that the native packages have been built or signed.
- Configure any production-only secrets in Cloudflare/GitHub secret stores. Never place API tokens in frontend variables or commit them to source control.
